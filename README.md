# nr-authdomain-migrator

Copy users, groups, group membership and role grants from one New Relic authentication domain to another using NerdGraph. Pure Python 3, standard library only. Runs can be stopped and resumed.

- **Read-only on the source.** The current domain is never changed.
- **Dry run by default.** Nothing is written without `--execute`.
- **Idempotent.** Re-running creates only what is missing.
- **Reversible.** Everything created is recorded and can be rolled back.
- **Auditable.** Every run writes a detailed log.

## Requirements

- Python 3.9 or newer.
- Two authentication domains in the same organization: the current one (source) and the new one (target).
- A **User API key** that can manage users, groups and access grants in both domains (for example Authentication Domain Manager and Organization Manager).

```sh
export NEW_RELIC_API_KEY=NRAK-...    # keep out of source control and tickets
export NEW_RELIC_REGION=US           # or EU
```

## Quick start

```sh
python3 migrate.py domains                                        # find the domain IDs
python3 migrate.py preflight --source <SOURCE_ID> --target <TARGET_ID>  # checks key, domains, API; writes nothing
python3 migrate.py prepare --source <SOURCE_ID> --target <TARGET_ID>   # writes out/source.json and out/users.csv
# edit out/users.csv: set migrate=yes for the users to move
python3 migrate.py apply --domain <TARGET_ID> --in out/source.json --users-csv out/users.csv            # dry run
python3 migrate.py apply --domain <TARGET_ID> --in out/source.json --users-csv out/users.csv --execute  # migrate
python3 migrate.py verify --domain <TARGET_ID> --in out/source.json --users-csv out/users.csv           # check
```

Start with a pilot: `--user jane@example.com --execute` instead of `--users-csv`, then confirm that user's access by logging in through the new domain.

## Commands

| Command | Purpose |
|---|---|
| `domains` | List authentication domains |
| `preflight` | Check the API key, both domains and API support before starting (writes nothing) |
| `prepare` | Export the source and generate `users.csv` (read-only) |
| `export` | Export only |
| `users-csv` | Refresh `users.csv` from the current state of the target |
| `apply` | Create missing groups, grants, users and memberships |
| `verify` | Compare the target with the export |
| `rollback` | Undo what `apply --execute` created |

Exit code is non-zero if a write failed, a run was stopped, or `verify` found a difference.

**Options** (global options go before the command, e.g. `migrate.py --throttle-ms 200 apply ...`):

| Option | Applies to | Meaning |
|---|---|---|
| `--region US\|EU` | all | NerdGraph region |
| `--log-dir DIR` | all | Log location (default `out/logs`) |
| `--throttle-ms N` | all | Pause after each write, to stay under rate limits |
| `--max-failures N` | all | Stop after N failures in a row (default 10, 0 = never) |
| `--users-csv FILE` | apply, verify, rollback | Select users from the worksheet |
| `--user EMAIL` | apply, verify, rollback | Select users by email (repeatable) |
| `--group NAME` | apply | Limit to these groups (repeatable) |
| `--exclude-role NAME` | apply, verify | Leave a role out of the copy (repeatable) |
| `--skip-empty-groups` | apply, verify | Do not copy groups that have no members |
| `--skip-no-access` | apply, verify | Do not copy groups that have no role grants. A group-scoped grant (e.g. Group Admin) that points at a skipped group is reported as `WARNING SKIPPED` |
| `--no-users` | apply, verify | Groups and grants only, for SCIM targets |
| `--default yes\|no` | prepare, users-csv | Initial value of `migrate` |
| `--execute` | apply, rollback | Perform writes or deletes. Shows the target domain and asks you to type its name first |
| `--yes` | apply, rollback | Skip that question (needed when not run from a terminal) |
| `--allow-users-in-scim` | apply | Create users even though the target is SCIM-managed (normally use `--no-users`) |

## The worksheet (`users.csv`)

Generated by `prepare`; one row per user. **Edit only the `migrate` column** (`yes`/`no`) and keep the file closed while the tool runs.

| Column | Meaning |
|---|---|
| `email`, `name`, `user_type` | From the source (Basic, Core, Full platform) |
| `groups`, `account_count` | The user's groups, and how many accounts they reach through them |
| `migrate` | `yes` to move the user. Starts as `no` (or `--default yes`) |
| `in_new_domain` | Whether the user already exists in the target |
| `status` | `not selected` · `pending` · `migrated` · `partial` (missing from some groups) · `failed` · `in new domain` |
| `last_updated`, `note` | Refresh time; reason for `failed` or `partial` |

The worksheet **updates itself** after every `apply --execute` and `rollback --execute` (also after Ctrl-C). Your `migrate` choices are never changed. Refresh it any time with `users-csv --domain <TARGET_ID>`.

`migrate = no` never removes anyone; it only stops the tool adding that user. To remove users, see rollback.

## What apply does

1. Creates the groups of the selected users (only those groups), then their grants, then the users, then memberships.
2. Other members of those groups are not created unless also selected.
3. Skips anything already in the target. Group-scoped grants (e.g. Group Admin) are re-pointed at the matching target group by name.
4. Records each created object in `out/manifest-<timestamp>.jsonl` (needed for rollback; keep it).

**Copied:** users (name, email, type), groups, membership, role grants at account, organization and group scope, including data access policies. Custom roles are organization-level and are reused as they are.

**Not copied:** SSO/SAML and provisioning settings (configure them on the target domain); entity-scoped grants (reported as `WARNING`); anything owned by individual user records, such as user API keys and user-owned assets (for example dashboards), because users in the target are new records with new IDs. User API keys must be created again in the new domain. To move user-owned assets, open a New Relic Support case and ask for them to be migrated to the new domain.

## Rolling back

```sh
MANIFEST=$(ls -t out/manifest-*.jsonl | head -1)      # newest manifest, or set the file yourself
python3 migrate.py rollback --domain <TARGET_ID> --manifest "$MANIFEST"            # dry run
python3 migrate.py rollback --domain <TARGET_ID> --manifest "$MANIFEST" --execute  # undo everything in it
```

To remove only some users, mark them `migrate = no` and add `--users-csv out/users.csv` (or name them with `--user`):

```sh
python3 migrate.py rollback --domain <TARGET_ID> --manifest "$MANIFEST" --users-csv out/users.csv --execute
```

- Removes only what the manifest lists; never touches objects that already existed in the target, or the source.
- Selective mode removes a user only if the tool created them (SCIM- or UI-provisioned users are "left alone"), together with their memberships. Groups and grants stay, since others share them.
- Dry run by default; refuses a manifest from a different domain; resumable.
- If several runs created users, run it once per manifest.

## Batches and long runs

- Do a dry run first; it reports counts and "at least N write calls".
- Pilot, then batches (for example a few hundred users at a time), checking `users.csv` between batches.
- Writes run one at a time with progress, rate and time remaining. Run long jobs in `tmux`/`screen`/`nohup`.
- Interrupted or failed runs: fix the cause and run the same command again.
- The tool stops after 10 consecutive failures (expired key, permissions, outage) instead of failing through every user. 429 responses are retried with backoff; add `--throttle-ms` if throttling persists.
- Writes are not blindly retried. If a create times out, the tool checks the target and records the object if it exists; otherwise the log says `outcome unknown`.
- Grants are sent in batches of 50 per group.

## Logs

Each command writes `out/logs/<command>-<timestamp>.log` (owner-only). It records the tool version and command, every object created or removed with its ID, every API call with duration and retries, and every failure with the full API error. It never contains the API key but does contain user emails; send it when asking for support.

## Troubleshooting

| You see | What it means |
|---|---|
| `Set NEW_RELIC_API_KEY ...` | The API key variable is not set in this shell; export it and run again |
| `Target ... is SCIM-managed` | Use `--no-users`; SCIM creates the users. `--allow-users-in-scim` overrides |
| `Export file ... not found` / `not a valid export` | Run `prepare` or `export`, or point `--in` at the right file |
| `Stopped after N failures in a row` | See the last `FAILED` lines (key, permission, rate limit); fix and re-run |
| `outcome unknown` | A write timed out; users and groups are re-checked automatically. Otherwise run `users-csv` and check the status |
| `status = failed` / `partial` | See `note`; run `apply` again for those users |
| `WARNING SKIPPED grant` | A grant type the tool cannot copy; recreate it manually |
| `unsupported user type` | User not created; fix the type or add the user manually |
| `Group name ... appears N times` | Duplicate source group names are merged |
| `Cannot roll back, API does not match` | A needed call is missing; nothing was deleted |
| `Could not update users.csv` | File open in another program; close it and run `users-csv` |
| `Fix the worksheet first` | A `migrate` cell is not `yes`/`no`; lines are listed |

## Running both domains side by side

A person in both domains has two separate user records with separate access; nothing merges. Tell users which login to use, offboard in both domains until the old one is retired, and keep access changes in step.

## Files and security

`out/` holds `source.json`, `users.csv`, `manifest-*.jsonl` and `logs/`. They contain user emails and are written owner-only; keep them out of shared locations and source control (`.gitignore` already excludes `out/`).

## Development and status

Version: 1.0.0 (`python3 migrate.py --version`; see `CHANGELOG.md`). Tests: `python3 -I tests/test_migrate.py` (offline, no API calls).

The core flow was validated end to end in a New Relic test account (on a pre-release build): reading a domain, creating groups, users, memberships and grants (including a group-scoped Group Admin grant), and rolling it all back. The following are covered by offline tests only and have not yet been run against a live account: `preflight`, the typed confirmation for `--execute`, the SCIM safeguard, `--skip-empty-groups` / `--skip-no-access`, the worksheet and status updates, selective rollback, retry and failure-limit behavior, and volume handling. Always run `preflight`, then a dry run and a pilot, first.

Provided as is, without warranty. It writes to your New Relic organization when you pass `--execute`; review the dry-run output first.
